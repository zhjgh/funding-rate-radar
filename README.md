# funding-rate-radar

> Binance USDT-M 永续合约 · 全市场资金费率年化排行

一个零依赖的全栈小工具：拉取全市场永续合约的当期资金费率，换算成年化，按高低排序，
一眼看出**哪些合约正在被资金费率"加杠杆"、哪些在付费做空**。

---

## 为什么做这个

永续合约没有到期日，靠**资金费率（Funding Rate）**把价格锚定在现货上：

- 永续价格 > 现货价格 → 说明多头情绪过热 → 费率为正 → **多头付钱给空头**，抑制做多
- 永续价格 < 现货价格 → 说明空头情绪过热 → 费率为负 → **空头付钱给多头**，抑制做空

费率每 8 小时结算一次（部分合约 4 小时）。单次费率看起来很小（0.01%），
但换算成年化就是 **10.95%** —— 这就是为什么高频持仓的人会盯着费率做套利。

这个工具要解决的问题：**把 0.01% 这种无感的数字，换成一眼能判断的年化口径。**

## 核心逻辑

### 1. 数据源

```js
GET https://fapi.binance.com/fapi/v1/premiumIndex
```

这一个公开接口就够用，返回全市场永续合约的：

| 字段 | 含义 |
|---|---|
| `lastFundingRate` | 当期资金费率（小数，`0.0001` = 0.01%） |
| `nextFundingTime` | 下次结算时间戳 |
| `markPrice` | 标记价格（强平用） |
| `indexPrice` | 现货指数价格 |

### 2. 年化换算

```js
annualized = rate * 3 * 365 * 100   // 8h 结算 → 一天 3 次 → 一年 365 天
```

这是**单利粗算**，业内通用的快速口径，不是复利。真要算复利是 `((1 + rate) ** (3 * 365) - 1)`，
但对看盘来说没必要——量级判断用单利足够了。

### 3. 分层设计

| 层 | 职责 | 为什么不放前端 |
|---|---|---|
| `binance.js` | 抓取、归一化、60 秒缓存、失败降级 | 绕开浏览器 CORS；缓存避免反复打第三方接口 |
| `index.js` | 路由分发、静态文件、路径穿越防护 | — |
| `app.js` | 排序、渲染、倒计时、自动刷新 | 纯展示逻辑，不碰数据获取 |

**降级设计**：Binance 有区域限制，国内网络经常打不通。所以任何异常都自动落到
`mock.json` 快照，页面上会标黄点「离线演示数据」。**保证 demo 永远能演示**，
而不是在面试现场卡在 loading。

### 4. 为什么要过滤低流动性合约

Binance 当前有 **886 个** USDT 永续合约，直接按费率排序会得到一份没法看的结果：

- 前几名是 `USDBRL`（美元/巴西雷亚尔汇率）、`EWZ`（巴西股指 ETF）这类**法币与代币化股票合约**，不是加密资产
- 一堆刚上线的小币，单笔订单就能把费率打到 0.3%，年化三四百个点

所以做了两道筛选：

```js
.filter((x) => x.quoteVolume >= 10_000_000)   // 日成交额不足 1000 万 USDT 的不参与
.sort((a, b) => b.quoteVolume - a.quoteVolume)
.slice(0, 120)                                // 只取最活跃的 120 个
```

**这是业务判断，不是技术处理。** 低流动性合约的费率不反映真实多空力量，
摆在榜单前面只会误导决策。最终从 886 个里筛出 120 个，BTC / ETH / SOL 等主流合约都在榜。

### 5. 底部那些 -900% 是真的吗

是真的。极端费率通常出现在两种场景：新合约上线初期流动性薄，或者行情剧烈时多空严重失衡。

工具**不隐藏极端值**——真实交易里，-900% 的年化恰恰是最该被看到的风险信号
（说明有人正在用极高成本维持空头或做对冲）。

但讲的时候要补一句：**这类数字不能直接当套利机会**，因为费率随时会翻转，
而且高费率往往伴随着极差的盘口深度。

## 15 分钟讲解大纲

| 时间 | 讲什么 | 要点 |
|---|---|---|
| 0–2 min | **业务问题** | 永续合约没有到期日，靠什么锚定现货？引出资金费率 |
| 2–5 min | **机制** | 正费率 = 多头付空头，负费率 = 空头付多头；每 8 小时结算；年化 = `rate × 3 × 365` |
| 5–7 min | **产品视角** | 0.01% 是无感数字，年化 10.95% 才有决策价值 —— 这就是这个工具存在的理由 |
| 7–10 min | **数据层** | 一个公开接口拿全市场；为什么要过滤 `USDT` 后缀；为什么要按成交额筛前 120 个；缓存 60 秒 |
| 10–13 min | **前端** | 排序、强度条（相对最大绝对年化归一化）、倒计时每秒走但不整表重绘 |
| 13–15 min | **工程取舍** | 为什么零依赖；为什么要做 mock 降级；如果上生产会怎么改 |

**讲解时可以主动加分的两点**：

1. **"为什么不用 WebSocket"** —— 资金费率 8 小时才变一次，30 秒轮询绰绰有余，
   上 WS 是过度设计。**知道什么时候不该用复杂方案，比会用复杂方案更值钱。**
2. **"标记价格是拿来干嘛的"** —— 强平按标记价算，不按最新成交价，
   防止插针爆仓。这是交易所风控的核心设计。

## 设计取舍

| 决策 | 原因 |
|---|---|
| **零依赖** | 面试官/同事 clone 下来 `node server/index.js` 就能跑，不用等 `npm install` |
| **不用 React/Vite** | 页面只有一个表格，构建链的成本大于收益；原生 ESM 够用且更容易逐行讲 |
| **不用图表库** | 强度条用 CSS `width` 百分比就能表达，引入 ECharts 会让代码量翻三倍 |
| **后端做缓存** | 多人同时打开页面时只打一次第三方接口，避免被限流 |

> 生产环境如果要做完整交易看板，技术选型会换成 React + Vite + TanStack Query +
> WebSocket 增量推送，但那是另一个量级的需求，不适合 15 分钟讲完。

## 已知局限

- 只覆盖 Binance USDT-M，没接 OKX / Bybit 做多交易所对比
- 单利年化，不是复利
- 没有历史曲线（要看费率变化趋势需要落库）
- 极端年化（±200% 以上）未做特殊标记 —— 真实交易中需结合持仓量与盘口深度判断，不能直接当套利信号
- 离线快照的数据是硬编码的演示值，**不是实时行情**

## 可以继续做的方向

- 接入 OKX / Bybit，做**跨交易所费率差**——同币种费率差超过阈值就是套利信号
- 落库存历史，画费率曲线，标记极端值
- 加上「按持仓量加权」的费率，比单纯排序更接近真实资金成本
