# funding-rate-radar

> Bybit / Binance USDT 永续合约 · 全市场资金费率年化排行

一个零依赖的全栈小工具：拉取全市场永续合约的当期资金费率，换算成年化，按高低排序，
一眼看出**哪些合约正在被资金费率"加杠杆"、哪些在付费做空**。

线上预览：https://funding-rate-radar.app.workbuddy.host

---

## 为什么做这个

永续合约没有到期日，靠**资金费率（Funding Rate）**把价格锚定在现货上：

- 永续价格 > 现货价格 → 说明多头情绪过热 → 费率为正 → **多头付钱给空头**，抑制做多
- 永续价格 < 现货价格 → 说明空头情绪过热 → 费率为负 → **空头付钱给多头**，抑制做空

费率按周期结算：多数合约 8 小时一次，主流币常见 4 小时甚至 1 小时。
单次费率看起来很小（0.01%），但按 8 小时周期换算成年化就是 **10.95%** ——
这就是为什么高频持仓的人会盯着费率做套利。

这个工具要解决的问题：**把 0.01% 这种无感的数字，换成一眼能判断的年化口径。**

## 核心逻辑

### 1. 数据源：为什么 Bybit 优先

两个交易所都有公开接口，但**一次请求能拿到的信息量不一样**：

| | Bybit `v5/market/tickers?category=linear` | Binance `fapi/v1/premiumIndex` |
|---|---|---|
| 覆盖合约 | 922 个线性合约，一次返回 | 886 个 USDT 永续，一次返回 |
| 当期费率 | `fundingRate` | `lastFundingRate` |
| **结算间隔** | ✅ `fundingIntervalHour`（1 / 4 / 8） | ❌ 接口不返回，只能假定 8h |
| 成交额 | ✅ `turnover24h` 同接口返回 | ❌ 要再请求 `ticker/24hr` 拼接 |

**`fundingIntervalHour` 是决定性差异。** 没有它就只能按 8 小时算年化，
一个 4 小时结算的合约年化会被少算一半，1 小时结算的少算 8 倍 —— 榜单排序直接失真。

所以 `PROVIDERS` 里 Bybit 排第一，Binance 只在前者失败时兜底（此时结算间隔按 8h 近似）。

### 2. 年化换算：按实际结算间隔

```js
const perYear = (24 / intervalHour) * 365;
annualized = rate * perYear * 100;
```

- 8h 结算 → 一天 3 次 → `rate × 3 × 365`
- 4h 结算 → 一天 6 次 → `rate × 6 × 365`
- 1h 结算 → 一天 24 次 → `rate × 24 × 365`

这是**单利粗算**，业内通用的快速口径，不是复利。真要算复利是 `((1 + rate) ** perYear - 1)`，
但对看盘来说没必要 —— 量级判断用单利足够了。

### 3. 分层设计

| 层 | 职责 | 为什么不放前端 |
|---|---|---|
| `sources.js` | 多源抓取、归一化、排名、60 秒缓存、三级降级 | 绕开浏览器 CORS；缓存避免反复打第三方接口 |
| `index.js` | 路由分发、静态文件、路径穿越防护 | — |
| `app.js` | 排序、渲染、倒计时、自动刷新 | 纯展示逻辑，不碰数据获取 |

### 4. 三级降级：demo 永远能演示

```
Bybit 实时  →  Binance 实时  →  snapshot.json（真实历史快照）  →  mock.json（手写兜底）
   绿点          绿点              灰点 + 抓取时间                  黄点
```

**为什么要有快照这一层**：这个项目部署在云上，而云环境的出网策略常常连不通交易所接口
（本地实测两个源都超时）。如果直接退回手写假数据，页面上就是一排编造的数字 ——
给面试官看的东西不能是这样。所以把本地抓到的一次真实行情存成 `snapshot.json`，
线上至少展示的是**真实市场价格，只是不实时**，并且明确标出抓取时间。

快照里存的是抓取当时的绝对时间戳，放着不动会变成过去时间、倒计时出现负数。
所以降级时按结算周期把 `nextFundingTime` 重新推到「下一个 UTC 整点结算时刻」——
交易所本来就按 UTC 整点结算，推算出来的时间与真实结算点一致：

```js
nextFundingTime = Math.ceil(Date.now() / period) * period;
```

### 5. 为什么要过滤低流动性合约

全市场有 **900+** 个线性合约，直接按费率排序会得到一份没法看的结果：

- 前几名是 `USDBRL`（美元/巴西雷亚尔汇率）、`EWZ`（巴西股指 ETF）、`SOXL`、`SKHYNIX`
  这类**法币与代币化股票 / 商品的合约**，不是加密资产
- 一堆刚上线的小币，单笔订单就能把费率打到 0.3%，年化三四百个点

所以做了两道筛选：

```js
.filter((x) => x.quoteVolume >= 10_000_000)   // 日成交额不足 1000 万 USDT 的不参与
.sort((a, b) => b.quoteVolume - a.quoteVolume)
.slice(0, 120)                                // 只取最活跃的 120 个
```

**这是业务判断，不是技术处理。** 低流动性合约的费率不反映真实多空力量，
摆在榜单前面只会误导决策。筛选后 BTC / ETH / SOL 等主流合约都在榜。

> 代币化股票类合约（`XAU`、`SOXL`、`SKHYNIX`）是交易所真实上线的品种，同样有资金费率，
> 榜单里混着出现不是数据串了。2026 年各家都在上 RWA 永续，这本身就是个可以聊的行业变化。

### 6. 底部那些 -4500% 是真的吗

是真的。榜尾 `AXISUSDT` 单期费率 **-2.06%**、4 小时结算，`-0.0206 × 6 × 365 ≈ -4512%`。
这不是算错，而是小市值 / 新上市合约允许更宽的费率上限。

工具**不隐藏极端值** —— 真实交易里，这种年化恰恰是最该被看到的风险信号
（说明有人正在用极高成本维持空头或做对冲）。

但讲的时候要补一句：**这类数字不能直接当套利机会**，因为费率随时会翻转，
而且高费率往往伴随着极差的盘口深度。

## 15 分钟讲解大纲

| 时间 | 讲什么 | 要点 |
|---|---|---|
| 0–2 min | **业务问题** | 永续合约没有到期日，靠什么锚定现货？引出资金费率 |
| 2–5 min | **机制** | 正费率 = 多头付空头，负费率 = 空头付多头；1h/4h/8h 三种结算周期 |
| 5–7 min | **产品视角** | 0.01% 是无感数字，年化 10.95% 才有决策价值 —— 这就是工具存在的理由 |
| 7–10 min | **数据层** | Bybit 一次请求就带 `fundingIntervalHour`；为什么按实际间隔年化；为什么筛掉低流动性 |
| 10–13 min | **前端** | 排序、强度条（相对最大绝对年化归一化）、倒计时每秒走但不整表重绘 |
| 13–15 min | **工程取舍** | 为什么零依赖；三级降级怎么设计的；如果上生产会怎么改 |

**讲解时可以主动加分的三点**：

1. **"为什么不用 WebSocket"** —— 资金费率 8 小时才变一次，30 秒轮询绰绰有余，
   上 WS 是过度设计。**知道什么时候不该用复杂方案，比会用复杂方案更值钱。**
2. **"标记价格是拿来干嘛的"** —— 强平按标记价算，不按最新成交价，
   防止插针爆仓。这是交易所风控的核心设计。
3. **"为什么每个合约的结算周期不一样"** —— 主流币流动性好、价格更容易被操纵，
   交易所就把结算周期缩短到 1h/4h 来抑制单边挤压。这是风控参数，不是随意配置。

## 设计取舍

| 决策 | 原因 |
|---|---|
| **零依赖** | 面试官/同事 clone 下来 `node server/index.js` 就能跑，不用等 `npm install` |
| **不用 React/Vite** | 页面只有一个表格，构建链的成本大于收益；原生 ESM 够用且更容易逐行讲 |
| **不用图表库** | 强度条用 CSS `width` 百分比就能表达，引入 ECharts 会让代码量翻三倍 |
| **后端做缓存** | 多人同时打开页面时只打一次第三方接口，避免被限流 |
| **快照而非假数据** | 降级时优先用真实历史快照，并在页面上标明抓取时间，不拿编造数字糊弄人 |

> 生产环境如果要做完整交易看板，技术选型会换成 React + Vite + TanStack Query +
> WebSocket 增量推送，但那是另一个量级的需求，不适合 15 分钟讲完。

## 已知局限

- 只做了 Bybit + Binance 两家，没接 OKX 做**跨交易所费率差**对比
- 单利年化，不是复利
- 没有历史曲线（要看费率变化趋势需要落库）
- 极端年化（±200% 以上）未做特殊标记 —— 真实交易中需结合持仓量与盘口深度判断，不能直接当套利信号
- 部署在云上时受出网策略限制，通常只能跑在 `snapshot.json` 上：**数据真实但非实时**，页面会明确标注
- `snapshot.json` 需要手动重新生成，没有做定时刷新

## 可以继续做的方向

- 接入 OKX，做**跨交易所费率差** —— 同币种费率差超过阈值就是套利信号
- 落库存历史，画费率曲线，标记极端值
- 加上「按持仓量加权」的费率，比单纯排序更接近真实资金成本
- 给快照加个定时任务，每天重新抓一次，线上就不会停在同一个时间点
